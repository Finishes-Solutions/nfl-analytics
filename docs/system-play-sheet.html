BALLDONTLIE NFL API

Ingestion · Azure Functions (TypeScript) · rate-limited 550/min
Three Tempos, One Client
  • Backfill — one-time, 2002→now, all season types, resumable via sync_state. Coverage probe first: coverage_map records what actually exists per endpoint/season before a single bulk request is spent.
  • Nightly — timer trigger: current-season games, box scores, aggregates, standings, advanced; daily injury + roster snapshots; active-player sweep.
  • Game day — 1–15 min cadence, only for games in a live window (started <6h ago / starting <1h). Scores, box scores, plays tail, odds + props snapshots.

Writes are idempotent: keyed tables via OPENJSON → MERGE, snapshot tables append-only. Overlapping runs are safe.

Azure SQL · single database, single-digit GB · schema generated from tables.ts
The Warehouse — 20 Tables + Views
  • Raw layer — every API field as a typed column, plus raw_json verbatim on every row. Nothing the API sends is ever dropped, even undocumented fields.
  • Semantic layer (views) — fantasy points (std / half / full PPR, computed not stored), rolling trends, usage share, matchup difficulty, season-over-season deltas. This is what the LLM and dashboard actually query.
  • Two principals — nfl_ingest (read/write, used only by ingestion) and nfl_readonly (DENY writes — every consumer below).
AI Access · Model Context Protocol
Custom MCP Server

Runs as nfl_readonly with row limits + statement timeouts. Two stages:

  • Stage 1 — generic SQL MCP (text-to-SQL over the views) to learn what you actually ask.
  • Stage 2 — curated tools: get_player_trends, compare_players, get_matchup_analysis. No hallucinated joins.

Consumers: Claude (Desktop/app), Copilot Studio (MCP support), any other MCP-capable model.

Frontend · Azure App Service (no Vercel)
Next.js Dashboard
  • API layer — parameterized queries, whitelisted sortable columns. Sort / filter / compare any metric across players, teams, seasons.
  • Live feel — v1: client polls your own API every 10–20s. v2: ingestion publishes "game N updated" to Azure SignalR; browsers refetch just that slice.
  • Zero API cost — a thousand open dashboards = 0 BALLDONTLIE requests. Freshness is decoupled from the rate limit entirely.

Tempo — Cadence & Rate Budget

Training Camp

BACKFILL · RUN ONCE

2002→now, every endpoint, every season type. ~1–2 hours wall clock at 550/min, dominated by plays (~1 paginated fetch per game) and player box scores (~25k rows/season). Checkpointed per season — kill and resume freely.

Film Review

NIGHTLY · TIMER 06:00 UTC

Refresh current season, re-aggregate, snapshot injuries + rosters. A few hundred requests, minutes of runtime. Also the daily archive tick for depth-chart and injury history the API deletes.

No-Huddle

GAME DAY · EVERY 1–15 MIN

Live-window games only. Off-hours runs cost one DB query and zero API calls. Snapshots odds + props every cycle — the unrecoverable data.

Flags on the Field — Honest Caveats

🚩 Known risks before kickoff

  • Historical depth is unverified until the probe runs. Advanced stats can't predate tracking (~2016); plays and team stats likely have their own floors. The system is built to respect coverage_map, not the marketing claim.
  • The OpenAPI spec is stale — schema here is the union of spec + docs, and raw_json catches whatever neither documents. Expect a field-shape surprise or two on first live contact.
  • Props are unrecoverable — no historical props exist upstream. Every game-day cycle you don't run is archive lost forever. Start the snapshot job before you care about the analysis.
  • "Live" has an upstream ceiling — your poll can outrun their refresh. Measure before tightening cadence.
  • Player age/height/weight are current snapshots, not historical; no birthdate field exists, so per-season age is an approximation.
  • Fantasy points & projections don't exist in the API — scoring is computed in views; projections are a build, not an import.
